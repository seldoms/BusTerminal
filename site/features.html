01 / 发现

发现与元数据缓存

配置里启用多个来源，按编号统一检索、聚合去重；不启用的来源完全不参与链路。

元数据与封面首次抓取后落库，之后浏览、翻页、看详情全是本地读 —— 回源抓一次详情往往要几十秒，而成熟库是六位数起步。

设计取舍

  • 缓存优先，回源是例外而不是默认路径
  • 缓存缺失时才降级：译文 → 库内标题 → 原始标题
  • 缓存目录是重要资产，必须持久化并纳入备份

02 / 翻译

标题中文化

用本地大模型批量翻译，支持后台回填历史数据。走本地而非云端：量级上百万条，内容本身也不适合外发。

翻译带质量闸。厂牌名、专有名词被字面直译成不相干的词，比原文更难读 —— 不合格的译文直接丢弃，保留原文。

质量规则

  • 作品名意译，艺人姓名保留原文
  • 过短的译文、纯片假名原文、仍含假名的译文一律不采用
  • 坏译文按实测句式拦截，不用宽泛关键词（会误杀）
  • 写入路径与批次校验共用同一道闸门

03 / 下载

磁链与下载调度

按可用性、体积、来源列出候选磁链，选中后下发给你自己的下载器，并在库内记下“谁下的、下到哪、什么状态”。

下载不是终点。做种达标后自动投放进整理入口，停在哪儿、为什么停，界面上都能看到。

衔接方式

  • 通过下载器的 Web API 交互，不接管它的数据
  • 按标签归类，便于和已有任务区分
  • 投放动作有前置条件，未达标不会误触发

04 / 入库

入库闭环

项目最核心的一段：把“下载完成”推进到“能在媒体库里播放”，全程可验证。

  • 投放文件
  • →
  • 触发整理
  • →
  • 重新刮削
  • →
  • 归类归档
  • →
  • 刷新媒体库
  • →
  • 回写状态
顺序不能乱。归档通知必须在投放之后，整理任务只接受库内绝对路径 —— 这类顺序依赖最容易踩，也正是把它做成闭环而不是脚本堆的理由。

05 / 维护

库状态与清理

本地文件清单

实体文件与元数据对齐，哪些条目只有记录、没有文件，一眼可见。

删除保护

删除与媒体服务器联动，带保护判定和顺序约束，没有“一键误删”。

滞留检测

下完却长期没入库、整理匹配不到内容 —— 静默失败会被主动挑出来。

06 / 部署

部署与凭据安全

首次启动进入引导向导，把接口授权、下载习惯、屏蔽词、缓存策略一次配齐；未完成向导前其它页面不开放。

鉴权可开关；库内敏感配置（API Key、口令、令牌）支持加密存储，启动时检测明文凭据并提示，不静默放过。

部署形态

  • 单容器 + SQLite：最快，适合试水
  • Compose + PostgreSQL：长期运行的推荐形态
  • 全栈 Compose：连下载器、刮削整理与媒体服务器一起装
  • 已装的服务可复用或跨机接入，不必重装

07 / 接口

可观测性与 API

仪表盘汇总各段健康度；后端接口文档完整，便于二次集成或当成可编排的服务使用。
